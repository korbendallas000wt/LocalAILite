## 2. Что сделано в этой сессии (фиксы, ещё НЕ закоммичены)

### 2.1. step_models.py — запуск Ollama сервера перед `ollama pull`
Проблема: `ollama pull` требует запущенного сервера, инсталлер его не запускал.
Решение: добавлены методы `_is_ollama_server_running()`, `_start_ollama_server()`, `_wait_ollama_ready()`. Метод `_pull_ollama_model()` теперь: проверяет порт 11434 → если не запущен, запускает `ollama serve` с env OLLAMA_MODELS → ждёт готовности (30 сек) → скачивает модель → останавливает сервер (только если сам запустил). Если сервер уже запущен пользователем — использует его, не останавливает.

### 2.2. step_models.py — HF cache формат для SDXL
Проблема: `snapshot_download(local_dir=...)` скачивал файлы напрямую, реестр v2.0 не распознавал модель.
Решение: заменено на `snapshot_download(cache_dir=...)`. Модель скачивается в формат `models--org--name/snapshots/{hash}/`, который реестр распознаёт как тип `hf_cache`.

### 2.3. advisor.py — Dreamshaper XL Turbo вместо SDXL Base
Проблема: `stabilityai/stable-diffusion-xl-base-1.0` требует принятия лицензии через веб-интерфейс HF. Без токена скачивание падает с 401/403.
Решение: дефолтная рекомендация сменена на `Lykon/dreamshaper-xl-v2-turbo` (без лицензии, скачивается сразу). SDXL Base оставлен в альтернативах с пометкой «⚠ Требует принятия лицензии HF».

### 2.4. Бэкап
Создан: `Backup/pkg_manager_20260809_204205` (detector.py, step_env.py, advisor.py, cli.py)

## 3. Тест на Fedora 44 (реальное железо)

Корбен установил Fedora Workstation 44 на 100 GB раздел, не виртуалка. Диагностика:

| Параметр | Значение |
|---|---|
| Ядро | 6.19.10-300.fc44.x86_64 (загрузилось на Xeon E5450!) |
| Python | 3.14.3 системный (pip не установлен по умолчанию) |
| Пакетный менеджер | dnf5 версия 5.4.1.0 |
| SELinux | Enforcing (может блокировать бинарник Ollama) |
| CPU | Xeon E5450, без sse4_2/popcnt/avx/avx2 |
| GPU | AMD Radeon HD 7790 (без CUDA) |
| RAM | 15 GB, диск 84 GB свободно |

### Ключевые находки для инсталлера:
1. **Python 3.14 не совместим с torch/diffusers** — detector ищет 3.10-3.12, на Fedora его нет по умолчанию. Нужна инструкция: `sudo dnf install python3.12 python3.12-devel python3.12-pip`
2. **step_env.py хардкодит pacman** для установки системного PyQt6 — на Fedora нужен `dnf install python3-pyqt6`
3. **SELinux Enforcing** может блокировать запуск бинарника Ollama (скачанного из интернета). Возможное решение: `chcon` или предложение `sudo setenforce 0` (с разрешения пользователя)
4. **pip случайно установился** через PackageKit (система предложила). Это не критично, но показывает, что на чистой Fedora pip может отсутствовать
5. Репозиторий клонируется с GitHub: `git clone https://github.com/korbendallas000wt/LocalAILite.git`

## 4. Что осталось сделать (план на следующий чат)

### Автоматическое определение пакетного менеджера — 5 патчей

| # | Файл | Что делаем |
|---|---|---|
| 1 | installer/detector.py | Расширить `detect_os()`: + openSUSE (zypper), Rocky/Alma (dnf), Gentoo (emerge), Void (xbps). Сейчас только arch/debian/fedora |
| 2 | installer/detector.py | Добавить маппинг: `{pkg_manager: {install_cmd, noconfirm_flag, pyqt6_package}}` |
| 3 | installer/steps/step_env.py | Использовать pkg_manager из детектора вместо захардкоженного pacman. Для стратегии 'system': если PyQt6 не установлен — предложить установку через правильный пакетный менеджер (с sudo, с разрешения) |
| 4 | installer/advisor.py | Добавить пункт в вердикты: «Пакетный менеджер: dnf» |
| 5 | installer/cli.py | Показывать пакетный менеджер в шаге 0 (информационно) |

### Справочник пакетов PyQt6 по дистрибутивам:

| Дистрибутив | Пакетный менеджер | Пакет PyQt6 | Флаг неинтерактивности |
|---|---|---|---|
| Arch / Manjaro | pacman | python-pyqt6 | --noconfirm |
| Debian / Ubuntu | apt | python3-pyqt6 | -y |
| Fedora | dnf | python3-pyqt6 | -y |
| openSUSE | zypper | python3-pyqt6 | -y |
| Rocky / Alma | dnf | python3-pyqt6 (нужен EPEL) | -y |

### Логика step_env.py для стратегии 'system':
1. `can_use_pip_pyqt6()` → False (старый CPU)
2. `detect_system_pyqt6()` → проверяем, установлен ли системный PyQt6
3. Если установлен и работает → venv с `--system-site-packages` (как сейчас)
4. Если НЕ установлен → **НОВОЕ**: предложить установку через пакетный менеджер:
   - Определить pkg_manager из detect_os()
   - Показать пользователю: «Системный PyQt6 не найден. Установить через {pkg_manager}? (потребуется sudo)»
   - С разрешения: `sudo {install_cmd} {pyqt6_package}`
   - После установки повторить detect_system_pyqt6()
   - Если всё равно не работает (например, Fedora с x86-64-v2 сборкой) → честно сказать «не поддерживается»

## 5. Принципы работы (не менять)

- «Не навязываем, но помогаем максимально» — детектор честно говорит, что потянет машина
- Идемпотентность — повторный запуск пропускает уже установленное
- Спрашиваем и предлагаем, ничего не ставим насильно (sudo только с разрешения)
- Проверено на Xeon E5450 без AVX2/SSE4.2 — самое сложное тестовое железо
- Все правки — командой для терминала с проверкой применения
- Бэкапы в Backup/ перед правками

## 6. Подводные камни

- Git-репозиторий в Repo/, не в рабочей папке. Синхронизация через sync_repo.sh
- docs/ из рабочей папки вручную копировать в Repo/docs/ перед коммитом
- full_context.py перегенерируется через ./save_context.sh
- pip-PyQt6 падает на CPU без sse4_2/popcnt — использовать системный из пакетного менеджера
- Ollama данные в ~/.ollama, не в data/ollama
- На Fedora системный PyQt6 может быть собран под x86-64-v2 (требует SSE4.2) — тогда даже системный не заработает на Xeon E5450. Детектор это определит через detect_system_pyqt6().works
- dnf5 vs dnf4 — синтаксис команд может отличаться, проверить на Fedora
